# LaundryPro UAE — Full & Final Implementation Roadmap

> **Developer / Maintainer:** Magnificent Solution
> **Product:** LaundryPro UAE (LaundryPro Local — Offline-First Desktop ERP/POS)
> **Stack:** Flutter Windows · PHP 8.x (Slim/Lumen) · MariaDB/MySQL · XAMPP · ESC/POS
> **Architecture:** MVVM + Modular Local Service Components · Offline-First · JWT/OAuth2
> **Roadmap Date:** 2026-09-09 | Based on full README.md (1,881 lines) audit

## 📌 CRITICAL RULES (Never Violate)

1. Never store monetary values as floating-point (`DECIMAL(18,2)` only).
2. Never update posted invoices — use correction memos only.
3. Never delete inventory movement records — soft-delete only.
4. Never hardcode English UI strings in widgets — all strings from `en.json`/`ar.json`.
5. Never do client-only authorization — all permissions enforced server-side by PHP middleware.
6. Never embed manufacturer-specific hardware logic inside business services — adapter interfaces always.
7. Every status transition is permission-controlled and audit-logged.
8. All backup/file paths come from standalone global configuration — never hardcoded.

### 7.7 Connectivity Auto-Discovery Algorithm
```
Step 1: Load saved hardware_config.json — attempt reconnect to each saved device
Step 2: If reconnect fails → add to "needs attention" list → show in status bar

Auto-Discovery Wizard (manual trigger):
  1. WMI query: SELECT * FROM Win32_PnPEntity WHERE PNPClass='Printer'
  2. BT: query paired Bluetooth devices, filter by device class 0x040680 (printer)
  3. TCP scan: for each IP in local subnet, try TCP connect to port 9100 (timeout 100ms)
  4. mDNS: listen for _pdl-datastream._tcp and _ipp._tcp service announcements
  5. COM ports: enumerate COM1-COM20, check for response to ESC/POS status command
  6. Present found devices → user selects type → saved to hardware_config.json

Auto-Bind:
  - Remember device: connection_type + identifier (IP, MAC, COM port, USB serial)
  - On app start: auto-connect to all saved devices in background thread
  - Retry interval: 30 seconds for failed connections
```

### 8.5 Retention Policy
```
Daily:   keep last 14 (configurable)
Weekly:  keep last 8 (configurable)
Monthly: keep last 12 (configurable)

Rule: Never delete the most recent successful backup merely because a newer attempt failed.
Rule: Label each backup with retention_tag (DAILY/WEEKLY/MONTHLY) at creation.
```

### 8.6 Restore Procedure
```
1. Admin opens Settings → Backup & Restore
2. Browse backup history (list from BACKUP_PATH)
3. Select backup file → system reads backup_manifest.json
4. Display: created_at, schema_version, record_counts
5. Verify SHA-256 hash of database.sql → if mismatch: ABORT
6. Check schema_version compatibility → if incompatible: ABORT
7. Confirm: "This will replace all current data"
8. System creates safety backup of current state (to BACKUP_PATH/pre_restore_YYYYMMDD.zip)
9. Stop API connections (graceful)
10. Restore database from database.sql
11. Verify record_counts match manifest
12. Restart API
13. Log restore event in audit_log
14. Success: show restored record counts
```

### 8.7 Disaster Recovery Targets
- **RTO** (Recovery Time Objective): < 4 hours
- **RPO** (Recovery Point Objective): < 24 hours (daily backup), < 1 hour if backup schedule shortened
