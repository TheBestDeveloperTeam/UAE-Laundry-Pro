# Change Request: Multi-Tenant Cloud Sync Enhancement for LaundryPro UAE

**Change Request ID:** CR-2026-09-02-001
**Date:** 2026-09-02
**Requested By:** Magnificent Solution (Individual Developer)  
**Priority:** High  
**Status:** Final Approved

---

## 1. Summary

This change request proposes an architectural enhancement to the LaundryPro UAE system to support a **multi-tenant cloud synchronization layer** while preserving the existing **local offline-first architecture**. The goal is to allow a single developer (Magnificent Solution) to deploy the same application flavor to multiple laundry business owners, each with their own local database, while optionally syncing their data to a central cloud database. Each business's data is strictly isolated using a unique `business_owner_id`. Local instances continue to function fully offline, with synchronization only transmitting the specific business's own data.

---

## 2. Background & Current State

Currently, the system is designed as a **single-tenant standalone desktop application**:

- **Local XAMPP** stack: Apache + PHP (Slim/Lumen) + MySQL/MariaDB.
- **Flutter Windows** desktop application, packaged as MSIX.
- Data resides entirely on the local machine.
- License validation via UMAC (hardware-bound).
- API endpoints are local, no cloud involvement.
- One installation per laundry business.

This works well for a single client but does not scale for a developer serving multiple laundry businesses without deploying separate codebases or servers.

---

## 3. Proposed Enhancement

### 3.1 High-Level Architecture

- Maintain the current local setup (XAMPP + MySQL + Flutter MSIX) for each business.
- Introduce a **cloud-based central database** (e.g., MySQL/PostgreSQL hosted on a cloud server) that aggregates data from all businesses.
- Each business is assigned a unique `business_owner_id` (tenant identifier) during registration.
- A **sync service** runs locally (as part of the API or a background process) to push local changes to the cloud and pull updates (if any) for the same business.
- Cloud database tables include a `business_owner_id` column to segregate data.
- Local database remains the primary source of truth; cloud is a backup/reporting repository.
- The local API is augmented with sync endpoints or a separate sync module.
- All existing functionality (POS, inventory, HR, etc.) remains unchanged from the user's perspective.

### 3.2 Data Synchronization Model

- **Pull/Push Limit**: Sync only data where `business_owner_id` matches the local business's assigned ID.
- **Conflict Resolution**: Use timestamps and a revision number; last-write-wins or configurable rules.
- **Incremental Sync**: Only changed records since last sync are transmitted.
- **Offline Behavior**: If no internet, local app functions normally; sync retries when connection is available.

### 3.3 Cloud Database Schema Changes

All relevant tables will include:

```sql
business_owner_id INT NOT NULL,
-- composite unique keys with business_owner_id + original primary key
```

Example for `customers`:

```sql
CREATE TABLE customers (
    id INT AUTO_INCREMENT,
    business_owner_id INT NOT NULL,
    name VARCHAR(255),
    ...
    PRIMARY KEY (id),
    UNIQUE KEY uq_business_customer (business_owner_id, local_customer_id)
);
```

A new `businesses` table will store registration details:

```sql
CREATE TABLE businesses (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255),
    contact_person VARCHAR(255),
    email VARCHAR(255),
    umac_code VARCHAR(255),
    license_key VARCHAR(255),
    active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 3.4 Sync Service

- Implement as a **PHP scheduled task** (e.g., every 5 minutes) or as part of the local API's background process.
- Use **OAuth2.0 client credentials** to authenticate with the cloud API.
- Cloud API exposes endpoints:

| Method | Endpoint                  | Description                          |
|--------|---------------------------|--------------------------------------|
| POST   | `/sync/push`              | Upload changed local records         |
| GET    | `/sync/pull?since={timestamp}` | Retrieve changes since last sync |
| POST   | `/businesses/register`    | Register a new business tenant       |

- Data payloads are JSON with `business_owner_id` and sync metadata.
- Local sync status is stored to allow resuming after interruptions.

### 3.5 Micro-Service API for All Businesses

The developer will maintain a single cloud API codebase that serves all businesses. It will:

- Validate `business_owner_id` on every request.
- Enforce data isolation using middleware.
- Provide aggregated reporting across businesses for the developer (admin only).

### 3.6 Local Application Changes

- Add a **sync configuration screen** in the Flutter app (hidden from regular staff, only admin).
  - Fields: cloud API URL, sync interval, last sync time, manual sync button.
- Display sync status (last successful sync, pending changes).
- License activation now also registers the business on the cloud server (optional).

### 3.7 Data Security

- All cloud communication over HTTPS.
- Sync tokens are scoped to a specific `business_owner_id`.
- Local database remains encrypted (if already implemented) or not shared.
- Cloud database uses row-level security or application-level filtering.

---

## 4. Benefits

- **Scalability**: One developer can support multiple laundry businesses with a single codebase.
- **Centralized Backup**: Cloud acts as an off-site backup for each business.
- **Remote Monitoring**: Developer can view business health and usage.
- **Future Features**: Enables cross-business analytics, centralized updates, and potential mobile apps.
- **Offline-First**: Each business remains fully functional without internet, preserving reliability.

---

## 5. Impact Analysis

### 5.1 Technical Impact

- **Database Schema**: Add `business_owner_id` to all local and cloud tables; local DB may keep existing structure but add a `local_id` mapping for sync.
- **API**: New sync endpoints; existing endpoints need to include `business_owner_id` context (from license).
- **Authentication**: Cloud API uses separate token system; local API still uses existing OAuth.
- **Performance**: Sync process should be efficient; incremental changes reduce load.
- **Complexity**: Increased development and testing effort, especially for conflict resolution and data mapping.

### 5.2 Resource Impact

- **Cloud Infrastructure**: Need a cloud server (e.g., VPS) with MySQL and API hosting.
- **Development Time**: Estimated additional 2-3 weeks for sync module, cloud API, and testing.
- **Maintenance**: Ongoing monitoring of sync failures and cloud server upkeep.

### 5.3 User Impact

- **Positive**: Automatic backup, potential for remote support.
- **Negative**: Slight increase in setup complexity (cloud configuration). But can be pre-configured or optional.

---

## 6. Dependencies & Assumptions

- The developer owns/manages the cloud server.
- Each business has a stable internet connection for sync (but not required for daily use).
- Local XAMPP installation remains as is.
- Flutter MSIX packaging continues.

---

## 7. Implementation Outline

1. **Design cloud database schema** and migration scripts.
2. **Develop cloud API** with tenant middleware, sync endpoints, registration.
3. **Modify local API** to track changes (using triggers or application-level hooks).
4. **Build sync service** as a PHP script with cron/scheduled task.
5. **Update Flutter app** to include sync settings and status display.
6. **Implement license-registration flow** to assign `business_owner_id`.
7. **Testing**: Multi-tenant isolation, offline sync, conflict resolution.
8. **Documentation** and deployment guide.

---

## 8. Risk & Mitigation

| Risk                              | Mitigation                                      |
|-----------------------------------|-------------------------------------------------|
| Data leakage between tenants      | Strict middleware and DB-level filtering        |
| Sync conflicts                    | Timestamp-based conflict resolution, manual override |
| Cloud server downtime             | Local continues to work; sync queues changes   |
| Performance degradation           | Incremental sync, background processing         |
| Unauthorized access               | OAuth2 client credentials, HTTPS, scoped tokens |

---

## 9. Acceptance Criteria

- A single cloud server can serve multiple business tenants.
- Each business's local data syncs to cloud with correct `business_owner_id`.
- Local app remains fully functional when offline.
- Sync is incremental and does not duplicate data.
- Cloud admin can view list of businesses and their sync status.
- No cross-tenant data is visible.
